# 图解计算机原理教程

> 目标：用“看得见的链路”理解计算机从按下电源到运行程序的全过程。
> 适合对象：嵌入式入门者、应用开发者、希望补齐底层基础的工程师。
> 学习方法：每章先看图，再理解关键概念，最后用验证任务闭环。

## 0. 总览：计算机到底在做什么

**一句话结论：计算机就是一个不断“取指令、解释指令、执行指令、保存结果”的状态机。**

```text
输入设备/网络/传感器
        │
        ▼
┌──────────────────┐
│      CPU          │  取指令、译码、执行、处理中断
└────────┬─────────┘
         │ 读/写
         ▼
┌──────────────────┐
│      内存 RAM     │  暂存程序、数据、栈、堆
└────────┬─────────┘
         │ 持久化
         ▼
┌──────────────────┐
│    存储 Flash/SSD │  保存程序、文件、固件
└────────┬─────────┘
         │ 控制
         ▼
┌──────────────────┐
│   外设/总线/IO    │  UART、SPI、I2C、CAN、GPIO、网卡
└──────────────────┘
```

### 你需要先建立的 4 个抓手

| 抓手 | 关注问题 | 工程意义 |
|---|---|---|
| 指令 | CPU 下一步要做什么 | 理解程序如何被执行 |
| 内存 | 数据和代码放在哪里 | 理解指针、栈、堆、越界 |
| 总线 | 模块之间如何交换数据 | 理解外设访问、寄存器、DMA |
| 中断 | 外部事件如何打断 CPU | 理解实时性、驱动、并发问题 |

## 1. 二进制：所有信息最终都落成 0 和 1

**结论：二进制不是为了“高级”，而是因为硬件最容易稳定地区分两种状态。**

```text
低电平 ≈ 0
高电平 ≈ 1

8 bit  = 1 byte
1024 B = 1 KiB
1024 KiB = 1 MiB
```

### 从电平到数据

```text
电平变化
  │
  ▼
bit: 0 / 1
  │  8 个 bit 组合
  ▼
byte: 0100 0001
  │  按编码解释
  ▼
字符: 'A'
```

### 常见误区

- `01000001` 本身只是 bit 组合；它可以被解释成字符 `'A'`，也可以被解释成整数 `65`。
- 数据含义不在 bit 本身，而在“解释规则”：编码、类型、协议、寄存器定义。

### 最小验证

```c
#include <stdio.h>

int main(void) {
    unsigned char x = 65;
    printf("as int=%u\n", x);
    printf("as char=%c\n", x);
    return 0;
}
```

通过标准：同一个字节 `65` 可以按整数或字符两种方式输出。

## 2. CPU：执行程序的核心状态机

**结论：CPU 不直接理解 C/Python/Java，它只执行机器指令。**

```text
┌──────────────┐
│  PC 程序计数器 │───► 指向下一条指令
└──────┬───────┘
       ▼
┌──────────────┐
│  取指 Fetch   │───► 从内存读取指令
└──────┬───────┘
       ▼
┌──────────────┐
│  译码 Decode  │───► 判断指令类型和操作数
└──────┬───────┘
       ▼
┌──────────────┐
│  执行 Execute │───► ALU 运算、访存、跳转、写寄存器
└──────┬───────┘
       ▼
┌──────────────┐
│  更新 PC      │───► 顺序执行或跳转
└──────────────┘
```

### 核心部件

| 部件 | 作用 | 类比 |
|---|---|---|
| PC | 保存下一条指令地址 | 书签 |
| 寄存器 | CPU 内部最快的小容量存储 | 手边纸条 |
| ALU | 做加减与逻辑运算 | 计算器 |
| 控制单元 | 指挥取指、译码、执行 | 调度员 |
| 状态寄存器 | 保存零标志、进位、中断使能等状态 | 仪表盘 |

### 工程抓手

调试 HardFault、非法指令、跑飞时，优先看：

1. `PC` 是否指向有效代码区。
2. `SP` 是否落在合法栈空间。
3. 异常发生前的返回地址 `LR`。
4. 访问地址是否越界或未对齐。

## 3. 内存：程序运行时的工作区

**结论：程序运行不是“直接在硬盘上跑”，而是代码和数据被加载到内存后，CPU 从内存取指令和访问数据。**

```text
高地址
┌──────────────────┐
│      栈 Stack     │  局部变量、函数调用现场，通常向低地址增长
├──────────────────┤
│                  │
│      空闲区       │
│                  │
├──────────────────┤
│      堆 Heap      │  malloc/new 动态申请，通常向高地址增长
├──────────────────┤
│   BSS 段          │  未初始化全局/静态变量，启动时清零
├──────────────────┤
│   Data 段         │  已初始化全局/静态变量
├──────────────────┤
│   Text/Code 段    │  程序指令、只读常量
└──────────────────┘
低地址
```

### 栈帧图解

```text
调用 main -> foo -> bar

┌──────────────┐
│ bar 栈帧      │  bar 的局部变量、返回地址
├──────────────┤
│ foo 栈帧      │  foo 的局部变量、返回地址
├──────────────┤
│ main 栈帧     │  main 的局部变量、返回地址
└──────────────┘
```

### 常见问题定位

| 现象 | 高优先级怀疑 | 验证方法 |
|---|---|---|
| 随机崩溃 | 栈溢出、越界写 | 打印/监控栈水位，开启栈保护 |
| malloc 失败 | 堆不足或碎片 | 记录申请大小、剩余堆、失败点 |
| 变量莫名变化 | 越界写、并发访问 | 对变量地址下 watchpoint |
| 重启后数据丢失 | 数据只在 RAM | 确认是否写入 Flash/文件系统 |

## 4. 编译和链接：源码如何变成可执行程序

**结论：编译器把源码翻译成目标文件，链接器把多个目标文件和库组合成最终可执行文件或固件。**

```text
main.c        driver.c        lib.a
  │              │              │
  ▼              ▼              │
预处理         预处理            │
  │              │              │
  ▼              ▼              │
编译           编译              │
  │              │              │
  ▼              ▼              │
汇编           汇编              │
  │              │              │
  ▼              ▼              ▼
main.o        driver.o       静态库
  └──────┬───────┴─────────────┘
         ▼
       链接
         ▼
   ELF / EXE / BIN / HEX
```

### 嵌入式中特别重要的链接脚本

```text
链接脚本决定：
- 代码放到 Flash 的哪个地址
- RAM 从哪里开始、大小是多少
- 栈顶在哪里
- 中断向量表放在哪里
- .text/.data/.bss 如何布局
```

### 工程抓手

- 编译通过 ≠ 固件能正确运行。
- 链接成功 ≠ 地址布局正确。
- 烧录成功 ≠ 启动代码、向量表、时钟初始化都正确。

## 5. 程序启动：从上电到 main

**结论：`main()` 不是 CPU 上电后的第一行代码；在它之前通常有启动代码完成硬件和运行环境初始化。**

```text
上电/复位
  │
  ▼
读取复位向量
  │
  ▼
设置 SP、PC
  │
  ▼
启动代码 Reset_Handler
  │
  ├─ 初始化时钟
  ├─ 拷贝 .data 到 RAM
  ├─ 清零 .bss
  ├─ 初始化 C/C++ 运行环境
  └─ 调用 main()
         │
         ▼
      应用逻辑
```

### 嵌入式调试重点

| 阶段 | 常见失败 | 观察点 |
|---|---|---|
| 上电复位 | 电源/复位不稳定 | 复位脚、电源轨、时钟源 |
| 取向量表 | 启动地址错误 | 向量表地址、Boot 配置 |
| Reset_Handler | 栈/内存初始化错误 | SP、PC、链接脚本 |
| main 前 | C 运行环境未准备好 | `.data`、`.bss`、全局构造 |
| main 后 | 业务初始化失败 | 外设初始化返回值、日志阶段 |

## 6. 总线和外设：CPU 如何控制外部世界

**结论：CPU 控制外设的本质通常是读写寄存器，而寄存器通过总线映射到地址空间。**

```text
CPU
 │  load/store 指令
 ▼
系统总线 AHB/APB/AXI
 │
 ├── RAM
 ├── Flash
 ├── GPIO 寄存器
 ├── UART 寄存器
 ├── SPI/I2C/CAN 控制器
 └── DMA 控制器
```

### 内存映射 IO

```c
#define GPIO_OUT_REG (*(volatile unsigned int *)0x40020014u)

void gpio_set_bit0(void) {
    GPIO_OUT_REG |= 0x1u;
}
```

这里的关键不是变量名，而是：

1. 地址 `0x40020014u` 是否真的是目标寄存器。
2. bit0 是否真控制目标 GPIO。
3. 该 GPIO 的时钟、复用、方向是否已正确配置。
4. `volatile` 防止编译器把寄存器访问优化掉。

### 外设问题排查顺序

```text
时钟使能
  │
GPIO/管脚复用
  │
寄存器配置
  │
中断/DMA/轮询方式
  │
外设实际电平或波形
  │
上层协议状态
```

## 7. 中断：外部事件如何打断当前执行流

**结论：中断是一种硬件驱动的异步事件机制，用来让 CPU 及时响应外部事件。**

```text
主程序正在运行
      │
      ▼
外设产生中断请求
      │
      ▼
CPU 保存现场
      │
      ▼
跳转到 ISR
      │
      ├─ 读取状态
      ├─ 清除中断标志
      ├─ 搬运少量数据/投递事件
      └─ 尽快退出
      │
      ▼
CPU 恢复现场
      │
      ▼
主程序继续运行
```

### ISR 最小原则

在中断里优先做：

- 清中断标志。
- 读取必要状态。
- 把事件放入队列或设置标志。
- 尽快返回。

避免在中断里做：

- 长时间循环等待。
- 阻塞式日志打印。
- 大量内存申请。
- 复杂协议解析。

### 中断调试关键点

| 问题 | 验证点 |
|---|---|
| 中断不进 | NVIC 使能、外设中断使能、优先级、全局中断 |
| 中断一直进 | 标志位未清、清除顺序错误、硬件条件持续存在 |
| 数据丢失 | ISR 处理太慢、队列满、缓冲区覆盖 |
| 偶发异常 | ISR 与任务共享变量未保护、重入、栈不足 |

## 8. DMA：让外设和内存直接搬数据

**结论：DMA 的价值是减少 CPU 搬运数据的负担，但它引入了缓冲区边界、同步和 Cache 一致性问题。**

```text
无 DMA：
外设寄存器 ──中断/轮询──► CPU ──写入──► RAM

有 DMA：
外设寄存器 ─────────DMA─────────► RAM
                         │
                         ▼
                  半传输/全传输中断
```

### UART DMA 接收典型链路

```text
UART RX 引脚收到数据
  │
  ▼
UART 接收寄存器
  │
  ▼
DMA 写入 rx_buffer
  │
  ├─ half complete 回调
  ├─ complete 回调
  └─ idle line 中断判断一帧结束
        │
        ▼
任务线程解析协议帧
```

### DMA 常见坑

| 坑 | 现象 | 验证方法 |
|---|---|---|
| 缓冲区太小 | 数据覆盖、帧错乱 | 记录写入位置和帧长度 |
| Cache 未同步 | CPU 读到旧数据 | invalidate/clean cache 后对比 |
| 回调里解析太重 | 后续数据丢失 | 回调只投递事件，任务里解析 |
| 半包当整包 | 协议解析失败 | 增加帧头、长度、校验、超时判断 |

## 9. 操作系统：把 CPU 时间分给多个任务

**结论：操作系统的核心价值是管理 CPU、内存、设备和并发。RTOS 更强调确定性和实时响应。**

```text
应用任务 A       应用任务 B       通信任务
    │               │              │
    └──────┬────────┴──────┬───────┘
           ▼               ▼
       调度器 Scheduler   IPC：队列/信号量/事件
           │
           ▼
        CPU 时间片/优先级切换
```

### 任务、队列、事件的职责边界

| 机制 | 适合传什么 | 不适合做什么 |
|---|---|---|
| 任务 | 独立执行流 | 过多任务导致调度复杂 |
| 队列 | 数据所有权转移 | 大对象频繁拷贝 |
| 事件标志 | 状态通知 | 携带复杂数据 |
| 信号量 | 资源计数/同步 | 保护复杂共享状态时语义不清 |
| 互斥锁 | 保护共享资源 | ISR 中阻塞等待 |

### RTOS 问题定位抓手

- 当前代码运行在 ISR、回调、定时器还是任务线程？
- 是否访问共享资源？谁写、谁读、谁清零？
- 队列是否可能满？满了是丢弃、覆盖还是阻塞？
- 高优先级任务是否长期占用 CPU？
- 低优先级任务持锁是否导致优先级反转？

## 10. 文件系统和存储：数据如何长期保存

**结论：RAM 断电丢失，Flash/SSD 等非易失存储才能长期保存数据；但持久化必须考虑擦写寿命、断电一致性和失败恢复。**

```text
应用数据
  │
  ▼
文件系统/键值存储
  │
  ▼
块设备驱动
  │
  ▼
Flash / eMMC / SSD
```

### 写入不是一步成功

```text
打开文件成功
  │
写入返回成功
  │
flush/fsync 成功
  │
文件系统元数据更新成功
  │
掉电后重新挂载仍可读
```

不要把“write 返回成功”直接等同于“断电后数据一定存在”。

### 存储验证闭环

1. 写入前记录路径、长度、校验值。
2. 写入后关闭并重新打开读取。
3. 比较长度和校验值。
4. 做掉电/重启后复读验证。
5. 记录失败恢复路径。

## 11. 网络和协议：数据如何跨设备传输

**结论：网络通信不是“发出去就成功”，必须分层确认每一段是否到达并被正确处理。**

```text
应用数据
  │
  ▼
应用协议：HTTP/MQTT/自定义协议
  │
  ▼
传输层：TCP/UDP
  │
  ▼
网络层：IP
  │
  ▼
链路层：以太网/Wi-Fi/蜂窝
  │
  ▼
物理层：电信号/无线信号
```

### 协议链路闭环

```text
发送请求
  │
  ▼
本地发送接口返回成功
  │
  ▼
对端收到帧
  │
  ▼
协议解析成功
  │
  ▼
业务执行成功
  │
  ▼
ACK/响应返回
  │
  ▼
本地状态更新
```

必须区分：

- 发送接口返回成功 ≠ 对端收到。
- 对端 ACK 成功 ≠ 业务最终生效。
- 本地状态更新成功 ≠ 云端最终确认。

## 12. 一条指令到一个外设动作：完整链路图

以“应用设置 GPIO 输出高电平”为例：

```text
应用调用 gpio_set(1)
  │
  ▼
驱动检查参数和状态
  │
  ▼
确认 GPIO 时钟已使能
  │
  ▼
确认管脚复用/方向为输出
  │
  ▼
写 GPIO 输出寄存器
  │
  ▼
总线事务到达 GPIO 控制器
  │
  ▼
GPIO 控制器改变输出锁存
  │
  ▼
芯片管脚电平变化
  │
  ▼
外部电路响应
```

### 每一层的成功标准不同

| 层级 | 成功标准 |
|---|---|
| 应用层 | 函数返回成功 |
| 驱动层 | 参数、状态、寄存器写入完成 |
| 总线层 | 总线访问未异常 |
| 外设层 | GPIO 控制器状态改变 |
| 硬件层 | 管脚实际电平变化 |
| 系统层 | 外部电路按预期响应 |

工程上不能只看函数返回值，关键动作要用寄存器读回、逻辑分析仪、示波器或外部反馈验证。

|---|---|---|
| 打印同一字节的整数和字符 | 理解数据解释规则 | 同一字节输出不同语义 |
| 递归压栈实验 | 理解栈增长和栈溢出 | 能观察到栈地址变化或栈溢出 |
| GPIO 翻转实验 | 理解寄存器到电平 | 示波器/逻辑分析仪看到波形 |
| UART 中断接收 | 理解中断链路 | 能统计进入 ISR 次数和接收字节 |
| UART DMA + idle | 理解 DMA 缓冲 | 能正确拆分不同长度帧 |
| RTOS 队列通信 | 理解任务间数据转移 | 生产者和消费者无丢包或有明确丢弃策略 |
| 文件写入重启读取 | 理解持久化 | 重启后校验值一致 |
| TCP/UDP 回环 | 理解协议分层 | 能区分发送成功和对端处理成功 |

## 16. 调试时的通用分层法

遇到“程序没按预期工作”时，不要直接猜代码问题，先分层定位：

```text
现象是否可复现？
  │
输入是否正确？
  │
协议/参数是否解析成功？
  │
状态机是否允许执行？
  │
本地执行是否成功？
  │
外设/系统是否真的生效？
  │
反馈/上报是否成功？
  │
对端是否确认？
```

### 最小日志建议

日志应尽量回答以下问题：

- 有没有进入该分支。
- 输入参数是什么。
- 当前状态是什么。
- 返回值是什么。
- 下一步走向哪里。
- 失败停在哪一层。
- 与预期状态差异在哪里。

示例格式：

```text
[GPIO][set] pin=5 value=1 clk=1 mode=output reg_before=0x00000000 reg_after=0x00000020 ret=0
```

## 18. 结束语

计算机原理不应该只停留在概念层。真正有工程价值的理解，是能把一个现象拆成可验证的链路：

```text
代码
  → 指令
  → CPU 状态
  → 内存访问
  → 总线事务
  → 外设寄存器
  → 硬件电平/存储/网络包
  → 业务状态
```

当你能在每一层说明“谁写、谁读、何时生效、如何验证”，你就不只是会用计算机，而是在理解计算机。
